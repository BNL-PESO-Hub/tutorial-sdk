# Troubleshooting

Most container problems come down to which [container backend](architecture.md#container-backends)
a command uses and which Docker daemon it reaches. Start with:

```bash
tutorial-sdk doctor
```

It shows which backends are usable, which one a command would select and why,
the daemon endpoint each backend uses, and the containers `tutorial-sdk` started
(see [`doctor`](cli.md#doctor)). Include its output when reporting a bug.

---

## No Container Backend Is Available

Without a usable backend, commands fail with an SDK error instead of a raw
`FileNotFoundError`. With `auto`, the messages are:

| Command | Exit code | Message |
| :--- | :---: | :--- |
| `build`, `ci` (`build`, `test`, `publish`, `all`) | `3` | `Build error: No container backend is available:...` (or for `ci` it is `Build failed:...`) |
| `validate --container` | `5` | `tutorial-sdk error: Docker is not installed or not on PATH.` |
| `run` | `5` | `tutorial-sdk error: No container backend is available:...` |

A backend selected explicitly reports its own reason instead, for example
`Docker is not installed or not on PATH.` for `docker-cli`.

In the Python API, `TutorialProject.build()` raises `BuildError`,
`validate(container=True)` raises `ValidationError`, and `run()` raises
`BackendUnavailableError`; all three derive from `TutorialSdkError`.

Install Docker and make sure the `docker` binary is on `PATH`, or install
docker-py (`pip install 'tutorial-sdk[docker]'`) and make sure the daemon is
running. When no backend is available, `validate --container` reports the
same message whatever the cause. When the `docker` binary is installed but
its daemon is not reachable, the Docker CLI backend is still selected: the
`container.start` check fails and the command exits with `1`.
`tutorial-sdk doctor` shows the actual reason in both cases.

## The `docker-sdk` Backend Is Not Available

`The 'docker-sdk' backend is not available: <exception>. Install the optional
dependency with pip install 'tutorial-sdk[docker]'.` means docker-py is not
installed in the environment that runs `tutorial-sdk`. With `auto`, this is
not an error: the Docker CLI is used instead. It is only reported when
`docker-sdk` was selected explicitly (`--backend`, `TUTORIAL_SDK_BACKEND`,
or `build.backend`).

## `docker-py` Cannot Find the Daemon

docker-py connects to `DOCKER_HOST` when it is set, and otherwise to the
default socket (`unix:///var/run/docker.sock`). Unlike the Docker CLI, docker-py
does not read Docker *contexts*, which Docker Desktop, Colima, and OrbStack
often use to expose their daemon. `tutorial-sdk` therefore falls back to the
current context's endpoint (`DOCKER_CONTEXT`, or the current context in the
Docker configuration) when `DOCKER_HOST` is unset and the default socket does
not answer, so both backends reach the same daemon.

The fallback only applies to contexts with a plain (non-TLS) endpoint. For a
TLS context, set `DOCKER_HOST` (and `DOCKER_TLS_VERIFY` / `DOCKER_CERT_PATH`)
yourself, or use `--backend docker-cli`. `doctor` prints the endpoint each
backend uses and its source (`DOCKER_HOST`, `context <name>`, or `default`).

If `DOCKER_HOST` points to an address that silently drops connections, `auto`
waits up to docker-py's 60-second client timeout before falling back to the
Docker CLI, and `doctor` waits the same way. Fix or unset `DOCKER_HOST`, or
select a backend explicitly.

## Build Fails with "requires BuildKit"

The docker-py backend builds with the Docker Engine's classic builder.
Dockerfiles that need BuildKit (`# syntax=` directives, `RUN --mount`, heredocs,
`$TARGETARCH`, and similar; see
[Native vs. Delegated `docker-sdk` Operations](architecture.md#native-vs-delegated-docker-sdk-operations))
are built through the Docker CLI when the `docker` binary is installed. Without
it, the classic builder rejects them (for example
`the --mount option requires BuildKit`) or, for directives it ignores such as
`# syntax=`, builds them without BuildKit's semantics.

Install the Docker CLI, or build with `--backend docker-cli`.

Dockerfiles generated by `tutorial-sdk` never need BuildKit; only
`build.custom_sections` snippets or hand-written Dockerfiles do. If
`tutorial-sdk doctor` reports `classic builder ... NOT served`, the Engine no
longer runs classic builds at all; use `--backend docker-cli` for builds.

## Build Output Format or Visibility

Builds are silent unless `--build-output` is given (see [`build`](cli.md#build)).
When a build fails without it, the output is part of the `Build error:...`
message.

The format depends on the backend: the docker-py backend shows the classic
builder's `Step 1/4 :...` lines, the Docker CLI typically shows BuildKit's `#1...`
lines.
Use `--backend docker-cli` if you need BuildKit's output. With the docker-py
backend, `BuildResult.digest` is the image ID; with the Docker CLI (including
builds the docker-py backend routes through it) it is `None`.

## `run --shell` Fails with the `docker-sdk` Backend

`The 'docker-sdk' backend performs interactive shell runs through the Docker
CLI, but the 'docker' binary was not found on PATH.` docker-py cannot attach a
terminal, so `--shell` always needs the Docker CLI. Install it; choosing
`--backend docker-cli` needs the same binary.

## `run` Shows No Output with the `docker-sdk` Backend

The docker-py backend reads the container's output from its logs. With a
logging driver that cannot be read back (such as `none`), it prints
`Container output unavailable:...` once; the container still runs and its exit
code is still returned. Use a readable logging driver (`json-file`, `local`)
or `--backend docker-cli`.

## Stopping `run` and Exit Code `125`

The first Ctrl-C asks the container to stop and prints
`Stopping container (interrupt again to force)...`. A container that does not
exit within 10 seconds, or a second Ctrl-C, makes `tutorial-sdk` kill and remove
it. With the Docker CLI backend, the run then ends with a `KeyboardInterrupt`;
with the docker-py backend, the command exits with the container's exit code.
See [`run`](cli.md#run).

Exit code `125` means the Docker daemon rejected the run before the container
started, as with `docker run` — for example, the host port is already
allocated (choose another `--port`) or the image cannot be found or pulled.
With the Docker CLI backend (and for `--shell`), errors from the `docker`
client itself keep the client's exit code: an unreachable daemon prints
`failed to connect to the docker API...` (or `Cannot connect to the Docker
daemon...`) and exits with `1`. Run `tutorial-sdk doctor` to see which daemon
each backend uses.

## Finding Containers Left Behind

Containers started by `tutorial-sdk run` carry the label
`org.bnl-peso-hub.tutorial-sdk.managed=true` on both backends. If the
`tutorial-sdk` process is killed (for example with SIGKILL), its container can
keep running. List such containers with either:

```bash
tutorial-sdk doctor
docker ps --all --filter label=org.bnl-peso-hub.tutorial-sdk.managed=true
```

and remove one with `docker rm -f <id>`. A listed container is not necessarily
orphaned — check that no `tutorial-sdk run` is still using it. A warning such
as `Warning: could not remove container <id>:...` after Ctrl-C also points to a
container to check.

Container validation does not label its containers. They are named
`tutorial-sdk-val-<name>`, and the next `validate --container` of the same
project removes a leftover one.

## Image Push Failures in CI

`ci --push` logs `Push failed: <message>` and continues; the run does not fail
(see [`ci`](cli.md#ci)). The message is the registry's or daemon's, the same
with both backends — for example `tag does not exist:...` or
`...connect: connection refused`.

- Credentials come from the Docker configuration and credential helpers, as
  for `docker push`. Run `docker login <registry>` first.
- A tag without a version is pushed as `:latest`.
- With the docker-py backend, a registry that sends no progress for 60 seconds
  aborts the push with `No progress from the Docker daemon while pushing...`.
  Retry, or push with `--backend docker-cli`.
